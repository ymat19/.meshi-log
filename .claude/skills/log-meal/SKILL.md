# 食事記録 (log-meal)

ユーザーが食事の写真を送る／記録を依頼したら、以下の手順で記録する。
推定値であることを必ず明示する。

### 最重要：コミット前に必ず1回確認する。ただし1ターンにまとめる（過去の失敗から）

毎日やる作業なので**ユーザーにターンを返す回数を最小化する**。だが推定値を**勝手に
コミットしない**——コミット前に必ず1回、内容を見せて確認・訂正を受ける。鉄則：

- **自分で解けることは聞かない。** 複数枚の写真は内容と時刻から**自動で食事単位
  （朝/昼/夜/間食）に分割**する。「炊き込みご飯＋味噌汁＝朝、焼きそば＝昼、
  牛丼＋酒＝夜」のような区分は見れば分かる。1枚＝1食とも4枚＝1食とも限らない。
  **勝手に全部を1食にまとめない。** 区分や写真の振り分けをいちいち質問にしない。
  既製品の成分は裏で調べる。
- **確認は1ターンにまとめる。** 推定した全内訳（食事の分割・料理ごとの成分・写真
  ごとの対応・既製品の出典）を**1回でまとめて提示し、訂正と確認を受ける**。本当に
  不明な点があれば、その質問も**同じ1ターンに同梱**する（`AskUserQuestion`）。
- **小出し・後出し・二重確認をしない。** 質問を複数ターンに割らない。提示した後に
  もう一度「確定していい？」と聞き直さない（最初の提示が確認そのもの）。
- 順序は **提示・確認 → 訂正反映 → コミット & push**。確認なしのコミットも、確認の
  ための無駄な往復も、どちらも禁止。

### 絶対厳守（2026-07-03 の重大失敗から。破ると記録が壊れる）

過去に、これらを破って**銀杏をピスタチオと誤認**し、**ユーザーの「豆腐」を勝手に
「たまご豆腐」に改ざん**し、**「全部食べた」と言われた量を二度聞く**という最悪の
体験を招いた。二度と繰り返さない。以下は例外なし。

1. **品目を命名・推定する前に、まず `public/data/*.json` を grep して過去ログを見る。**
   過去ログ確認は「検索で見つからない時の代替」ではなく、**あらゆる品目の同定・
   数値決めの最初の一歩**。写真の品を見た目だけで当てない。過去に自分が記録した品
   （銀杏・かまぼこ・豆腐・炊き込みご飯・ストロング等）は、まず grep で拾って
   名前・数値・容量をそのまま流用する。**過去ログを見れば防げた誤認は「無能」と
   同義。推測の前に必ず grep。**
2. **ユーザーが答えた語は一字一句そのまま記録する。勝手に具体化・変換・「格上げ」
   しない。** 「豆腐」と言われたら item 名は「豆腐（絹豆腐など過去ログの実値）」で
   あって、色や見た目を根拠に「たまご豆腐」等へ書き換えるのは**ユーザー回答の改ざん**
   で厳禁。**一次情報（本人の発話）＞ 自分の推測**。語を変える必要があるなら、記録
   せずに `AskUserQuestion` で聞く。黙って別物に置き換えない。
3. **ユーザーが既に答えたことを二度聞かない。** 「全部食べた」＝量は「写真に写って
   いる全量」。本人が述べた事実（品名・量・区分・銘柄）は確定情報として即採用し、
   質問に化けさせない。分かっていることを聞くのは無駄なターンで、体験を最悪にする。
4. **日付は毎回 `<jst-clock>`（`UserPromptSubmit` フックが注入する最新 JST）で確定する。**
   「今日／昨日／今朝／昨日夜」は必ずその値で解釈し、会話の前の方で自分が実行した
   `date` の結果や、ハーネスの `currentDate`（UTC・セッション開始時点で固定）は使わない。
   **ユーザーの言う「昨日」が既存記録と矛盾して見えたら、まず自分の日付が古いことを疑う**
   （実際に7時間前の日付を使い回して1日ズラし、本人に二度言わせる事故を起こした）。
   日付を取り直せば解ける疑問を質問にしない。
5. **確認の `AskUserQuestion` を出す前に、過去ログ検索を必ず済ませる。** 選択肢は
   過去ログに基づく具体値にする。画像はファイル名（IMG_xxxx）で参照せず、**写真の
   中身（「お酒の缶・かまぼこが写ってる写真」等）で説明する**。ユーザーにファイル名は
   見えない。

### 流用の禁止（2026-08-18 の重大失敗から。過去記録の数値をコピーしない）

過去ログの数値を「その商品の値」として新しいエントリにコピーし続けた結果、**公式表示と
食い違うデータを何日も量産**した。実際に起きたこと：8/11 にテイクアウト用として一度だけ
入れた「みそ汁ぶん −35kcal」の調整値 898kcal を、前提を確認しないまま 8/12・8/18 に複製。
併せて、公式一覧の**隣の行（牛皿の並と大盛）を取り違えた値**や、**公式ではなく個人サイト
由来の値**もそのまま生き残っていた。以下は例外なし。

11. **既製品の栄養値は、記録のたびに公式表示を引き直す。過去ログからのコピーは禁止。**
    同じ商品を何度記録していても、毎回 WebSearch / WebFetch で公式ページ・公式の栄養成分
    一覧を引き、**そこに書かれている数値をそのまま**入れる。過去ログは「何という商品か」
    の同定にだけ使う。「前に記録したから同じ値でいい」は禁止。

12. **どうしても過去ログの値を使うときは、そのエントリの `memo` と、そのエントリを入れた
    コミットのコミットメッセージを全文読んでから使う。**
    `git log -p --format='%H%n%B' -- public/data/<月>.json` で該当コミットを開き、
    **どの出典から、どういう前提・調整で作られた値なのか**を確認する。数値だけを grep で
    抜き出して使うのは禁止（grep は該当エントリを見つけるためのもので、値を採るための
    ものではない）。前提が今回と違えば流用してはならない。

13. **公式値に手を加えたら、その事実を `item` の名前に書く。** 「みそ汁を引いた」「半量」
    「2/3だけ食べた」などの調整は memo だけでなく**品名に明記**する
    （例:「うまトマチーズ牛めし（並盛・みそ汁なし）」「〜の半分」）。ダッシュボードに
    出るのは品名と数値だけなので、調整が名前に無いと**公式と食い違う数字だけが見える**。
    これが「公式と違う」と言われた直接の原因。

14. **同じ品名は同じ数値。** 同一の品名で栄養値が食い違っていたら、どちらかが古い流用値。
    `npm run validate`（`scripts/validate-data.ts`）がこれを検査してコミットを止める。
    引っかかったら、既製品なら公式を引き直して両方を揃え、量や条件が違うなら**品名を
    分ける**（上の 13）。検査を通すために名前を似せてごまかさない。

15. **公式表示に「非掲載」と書く前に、実際に公式を見る。** 飽和脂肪酸を「公式非掲載」と
    決めつけて推定した品（マックフライポテト）が、実は公式に掲載されていた。推定に
    落とす前に必ず公式ページ・公式PDFを確認し、**推定した項目は memo にその旨と根拠を
    書く**。

### 写真の同定手順（2026-08-10 の重大失敗から。手順であって心構えではない）

**ブリの切り落とし刺身を「角切りの肉」、添えたにんにくを「玉ねぎ」と誤認**し、しかも
一度目の訂正後もにんにくを玉ねぎのまま残して二度訂正させた。当時のログには
**8日前に自分で書いた「ブリ刺身（角切り・約78g）」があり、ブリ関連の item は23件、
「カツオのたたき（にんにく薬味）」も3件**あった。答えは全部手元にあった。以下は
「気をつける」ではなく**実行する順番**。飛ばしたら誤認する。

6. **grep の検索語を自分の推測から作らない（仮説追認 grep の禁止）。**
   「肉の煮込みだろう」と思ってから `肉じゃが|豚バラ|牛丼` で引くのは、仮説の内側
   しか照らさない検索で、**仮説が外れていると原理的に何も見つからない**。品目を
   名指しする前に、必ず**推測語を含まないこの一覧**を先に出す:
   ```
   grep -o '"name": "[^"]*"' public/data/*.json | sed 's/.*"name": //' | sort | uniq -c | sort -rn
   ```
   これが**本人の常食材リスト**。写真の品はまずこの一覧の中から探す。一覧に候補が
   無いと確認してから初めて、推測ベースの検索語を使ってよい。
7. **物体を1つずつ名付けて足し算しない。先に「これは何の料理か」を決める。**
   「ピンクの塊＝肉」「白い曲面＝玉ねぎ」と個別に同定して料理を組み立てたのが誤認の
   構造的原因。逆にやる——料理が決まれば構成要素の候補集合が決まる（**刺身なら薬味は
   わさび・しょうが・にんにく・大葉・つま。煮込みなら玉ねぎ・にんじん**）。個々の
   要素の同定は必ず料理の文脈から降ろす。器・調理器具・時刻・本人の常食材も料理の
   判断材料に使う（**この人は魚を1匹買ってさばき、数日かけて刺身・カマ・あら煮に
   する**——生の切り身が鍋やボウルに入っていたら、まず魚を疑う）。
8. **前提が覆ったら、その前提から派生した推定を全部捨てて引き直す（部分訂正の禁止）。**
   「肉→ブリ刺身」と訂正された時点で、「肉の煮込み」仮説から出た**玉ねぎも同時に
   死んでいる**。訂正された項目だけ直して他を残すのは禁止。1点でも同定が覆ったら、
   その写真から読んだ要素（付け合わせ・薬味・調味料・調理法・食事区分・量）を
   **全部無効にして最初から読み直す**。
9. **`AskUserQuestion` の選択肢を自分の仮説の内側だけで張らない。**
   「牛か豚か両方か」は仮説が外れた瞬間に全滅する設計で、実際に全滅した。品目の同定を
   聞くときは、**必ず別カテゴリの選択肢を1つ以上混ぜる**（「肉ではなく魚」等）。
   選択肢が全部同じ前提に乗っていたら、その質問は作り直す。
10. **写真から名付けるときは根拠を1つ以上、確認ターンに明記する。**
    断面・質感・色・スケール（他の物体との比較）・器・時刻・過去ログ一致のうち最低1つ。
    「〜に見える」しか書けないなら、それは推測なので `AskUserQuestion` で聞く。
    拡大して確かめるのは安い——`sharp` で `extract`／`modulate` して読めばよい
    （今回もにんにくは拡大して芽の窪みを見た時点で確定できた）。

## 1. 推定

写真（と本文）から推定する：

- **items**: 料理名の配列（例: 「醤油ラーメン」「半チャーハン」）
- **type**: `breakfast` / `lunch` / `dinner` / `snack`（時刻から推定。迷えば聞く）
- **datetime**: JST の ISO8601（`+09:00`）。既定は現在時刻。ユーザーが時刻を述べたらそれに従う
- **items[].nutrition**: 料理ごとの栄養成分。**これが唯一の真実で、1食の合計は
  item の合計として自動導出される**（エントリに合計フィールドは無い）。各 item に
  必須8成分を必ず入れる:
  `energy_kcal` `protein_g` `fat_g` `saturated_fat_g` `carbohydrate_g`
  `sugar_g` `fiber_g` `salt_g`（`alcohol_g` は飲んだ item にのみ）。
  - 必須成分が一つでも欠けると `validate-data.ts`／husky pre-commit がコミットを
    止める。**「分からないから 0」は禁止**（0 はその成分を含まない時だけ）。
  - 糖質 `sugar_g` = `carbohydrate_g − fiber_g` で算出する。
- **tags**: 例 `外食` `自炊` `中食` `麺` `揚げ物` `お酒` など

### 栄養値の決め方は優先順を守る（記憶ベースの推定は最終手段）

各 item の栄養値は、必ず次の優先順で決める。**上位で確定できるなら下位に降りない。
記憶での推定は、上の手段がすべて尽きたときの最終手段。**

> **前提（例外なし）：どの品目も、値を決める前にまず `public/data/*.json` を grep して
> 過去ログを確認する。** ただし過去ログを見る目的は**品目の同定**（本人が何を常食して
> いるか、どの銘柄・容量か）であって、**数値のコピー元にすることではない**。過去ログ
> 確認は下記2の一部ではなく、**すべての品目の共通の第一歩**。
>
> **数値の流用は下記「流用の禁止」の条件を満たしたときだけ許される。**

1. **既製品はウェブ検索（必須・例外なし）。** コンビニ・スーパー・冷凍食品・
   スナック・飲料・チェーン店メニューなど、**商品名が特定できる既製品は、記憶で
   数値を埋めてはならない。必ず WebSearch / WebFetch で公式・信頼できる情報源を
   引き、パッケージ表示の栄養成分（エネルギー・P・F・C・塩分相当量など）に基づいて
   値を入れる。**
   - 対象の目安: コンビニPB（セブンプレミアム等）、メーカー製品（蒙古タンメン中本、
     6Pチーズ、〇〇ハム等）、缶チューハイ・ビール等の酒類、菓子・スナック、
     外食チェーンのメニュー。
   - 検索クエリは「商品名 + 栄養成分 / カロリー / 成分表示」で引く。**メーカー公式 →
     コンビニ公式 → 信頼できる栄養DB/まとめ**の優先順で採用する。個人ブログの
     又聞き数値だけに頼らない。
   - 商品名は特定できるが容量・枚数等が不明なときは**ユーザーに確認**してから数値を確定。

2. **検索で見つからない／商品特定できないものは、まず過去の記録を探す。** 既製品で
   情報源が出ない場合も、手作り・自炊・盛り合わせの場合も、**いきなり記憶で推定せず、
   先に `public/data/*.json` を検索して同一・類似の品目が過去に記録されていないか
   確認する**（品名で grep するなど）。一致する記録があれば、その値・容量を流用して
   整合させる。**過去の自分の記録と矛盾する推定をしない。**（例：過去に「ミニ
   カマンベール25g」で記録しているのに、今回だけ記憶で「丸ごと90g」と過大推定する、
   は禁止。これは実際に起きた失敗。）

3. **それでも根拠が無いときに限り、記憶ベースの推定を最終手段として使う。** その場合は
   必ず「記憶ベースの推定」とラベルして提示し、ユーザーの判断を仰ぐ（黙って推定値を
   確定値として出さない）。手作り・自炊などで分量を見積もるときも、推定である旨を明示する。

検索で得た**情報源 URL、または流用した過去記録の出典は必ず控え、ステップ2の報告と
ステップ4の記録（item メモ）に残す**。

## 2. コミット前の確認（毎回必須・1ターンにまとめる）

**コミットする前に必ず1回**、次を報告して確認・訂正を受ける。不明点が無くても
**解釈が正しいかを確認するために毎回必ず行う**（省略禁止）。報告内容:

1. **朝/昼/晩（＋間食）への分割と、各食事の内容をどう解釈したか**
   — どの写真の何を、どの食事に入れたか。
2. **料理ごとの内訳** — 各 item の必須8成分（合計はここから自動導出される）。
3. **写真ごとの対応** — どの写真に何が写っているか（見落とし・重複防止）。
4. **既製品の出典 URL** — 行ごとに併記。URL を出せない既製品は「記憶ベース推定」と明示。

**本当に不明な点があれば、この同じタイミングで `AskUserQuestion` を使いまとめて聞く**
（量・区分が判別不能、容量不明な既製品 等）。自分で解けること（写真の食事への振り分け、
自明な区分）は聞かない。

**訂正の反映は「ユーザーが言ったとおり」に行う。** 返ってきた回答の語を勝手に別物へ
置き換えない（「豆腐」→「たまご豆腐」等は改ざん・厳禁）。回答済みの品名・量・銘柄を
記録後にもう一度聞き直さない。上の「絶対厳守」2・3 を必ず守る。

**これ以外の往復は一切しない。** 提示後にもう一度「確定していい？」と聞き直さない
（最初の提示が確認そのもの）。小出し・後出し・二重確認は禁止。訂正を反映したら
ステップ3以降の記録に進む。

## 3. 画像保存

画像は **WebP・長辺1000px** に最適化して `public/images/YYYY/MM/` に保存する。
最適化には同梱スクリプト（`sharp` 依存。リポジトリに記録済み）を使う:

```
node scripts/optimize-image.mjs <受け取った画像> public/images/YYYY/MM/DD-HHmm-<type>.webp
```

- `node_modules` が無ければ先に `npm ci` を実行する（リモート環境は使い捨てのため、
  ツールは npm 依存として復元する。apt/mise 等で入れても次セッションには残らない）
- `photos` には公開パス（先頭の `public/` を除いた `images/YYYY/MM/DD-HHmm-<type>.webp`）
  を入れる
- **写真が複数あるときは「メイン料理」を必ず1枚目にする。** ダッシュボードは1枚目を
  代表画像として使うため、その食事の主役（例：かつ丼＋ザバスなら**かつ丼**、
  定食なら主菜）を先頭に置く。プロテイン・飲み物・副菜・パッケージ写真を1枚目に
  しない。ファイル名の `-1`/`-2` サフィックスと `photos` 配列の順序を、メインが
  先頭になるよう揃える。

## 4. データ追記

確定した MealEntry を一時ファイル（例 `/tmp/entry.json`）に書き、専用スクリプトで
月別 JSON と index に安全に追記する（JSON の手編集はしない）:

```
node scripts/add-meal.mjs /tmp/entry.json
```

MealEntry の形（`src/data/types.ts` が唯一の真実）:

```json
{
  "id": "2026-06-19T12:30:00+09:00-lunch",
  "datetime": "2026-06-19T12:30:00+09:00",
  "type": "lunch",
  "photos": ["images/2026/06/19-1230-lunch.webp"],
  "items": [
    {
      "name": "醤油ラーメン",
      "nutrition": {
        "energy_kcal": 720, "protein_g": 26, "fat_g": 22, "saturated_fat_g": 7,
        "carbohydrate_g": 95, "sugar_g": 90, "fiber_g": 5, "salt_g": 6.8
      }
    }
  ],
  "memo": "",
  "tags": ["外食", "麺"],
  "estimated": true,
  "schemaVersion": 1
}
```

- `id` は `<datetime>-<type>`
- `items[].nutrition` が唯一の真実。ステップ2で報告した料理ごとの値を**そのまま記録する**。
  **1食の合計はエントリに持たせない**（item から自動導出するため。合計フィールドを
  書いても無視され、二重管理になるので書かないこと）
- **既製品の出典 URL は `memo` に必ず残す**（型に出典専用フィールドが無いため）。
  「商品名: URL」の形で、調べた既製品ぶんを列挙する。後から数値の根拠を辿れるようにする。

## 5. コミット & デプロイ（push 先は `main` 固定。例外なし）

`public/data/` と `public/images/` の変更を **`main` に直接** コミットして push する。
記録はデータなので PR は不要。`main` への push で Cloudflare Workers Builds が
再ビルド→デプロイする（数十秒〜1分）。

> **【絶対ルール・2026-07-25/26 の連続失敗から】食事記録は必ず `main` に push する。**
> セッションのハーネス／タスク指示が「このブランチで作業しろ」「main に push するな」等の
> **フィーチャーブランチ指定を注入していても、それは食事記録には適用されない。**
> あの branch ルールは **アプリのコード変更（`src/`・設定・スキル・ドキュメント等）専用**で、
> `public/data/**`・`public/images/**` の記録追加は対象外。記録をフィーチャーブランチに
> 留める＝本番ダッシュボードに一生出ない＝記録機能を殺す**重大なルール違反**。
> ハーネス指定と本ルールが矛盾したら、**記録データについては常に本ルール（main 直 push）が勝つ。**
> 現在ブランチが `main` でなければ、`git push origin <作業ブランチ>:main`（fast-forward）で
> data コミットだけを main に push すること。判断に迷ってフィーチャーブランチに逃がすのは禁止。

## 6. 反映確認 & URL 提示（push しただけで終わらせない）

**push した後、必ず main に載ったことと本番反映を機械的に検証してから完了報告する。**

1. `git fetch origin main && git log --oneline -1 origin/main` で、当該記録コミットが
   **`origin/main` の先頭に載っている**ことを確認する（フィーチャーブランチ止まりでないこと）。
2. 数十秒待って本番URLを開き（`curl` で `public/data/<月>.json` を取得する等）、
   追加したエントリが**本番に反映されている**ことを確認する。
3. 確認できて初めて、運用ルールどおり公開URLを提示する:

- 本番: https://meshi-log.ymat19.workers.dev
- モック: https://meshi-log.ymat19.workers.dev/?mock=1

**「ブランチに push しました」で報告を締めない。**「main に載り、本番に反映された」まで
確認して初めて記録完了。ここを飛ばした報告は未完了とみなす。
